Regular bugs, documentation typos, or improvement suggestions should be reported normally as an [Issue on GitHub](https://github.com/mateuszkarpierz/secret-key/issues) — that's the standard way, nothing secret about it. This page covers **security vulnerabilities only** (see [reporting scope](#-reporting-scope) below) — please do **not** report those publicly.

---

## 📬 Reporting security vulnerabilities

> [!CAUTION]
> Report security vulnerabilities privately only, to **dev@secretkey.website** — never as a public GitHub Issue. Publicly disclosing an exploit before a patch is released puts everyone running the system at risk.

### How to report

Send a detailed description to: **dev@secretkey.website**

### What to include in your report

| | Element |
|---|---|
| 📝 | Description of the vulnerability and its potential impact |
| 🔁 | Steps to reproduce (proof of concept) |
| 🏷️ | Affected system version |
| 💡 | Suggested fix *(optional)* |

### What to expect

| Time | Response |
|---|---|
| **48h** | Acknowledgment of receipt |
| **7 days** | Update on progress |
| After the fix | Public acknowledgment *(if you'd like)* |

## 🏷️ Supported versions

The **latest released version** is always supported. Reports concerning older versions are welcome, but please update to the latest release first — some vulnerabilities may already be fixed.

You can find the current version on the [Releases page](https://github.com/mateuszkarpierz/secret-key/releases).

## 🎯 Reporting scope

### ✅ In scope

- Authentication bypass (bcrypt, 2FA)
- CSRF vulnerabilities despite the protections in place
- Ability to reconstruct the Shamir secret without the required number of shares
- Exposure of data from the `/private/` directory
- Downloading sensitive files (e.g. the password database) while bypassing login, e.g. via a direct URL
- Susceptibility to brute-force attacks despite rate limiting
- XSS, SQL Injection *(although the system doesn't use SQL)*

### ❌ Out of scope

- Attacks requiring physical access to the server
- Social-engineering attacks against Secret Key card holders
- Web server configuration issues on the user's side
- Reports auto-generated by scanners without a PoC

## 🛡️ Deployment best practices

> [!WARNING]
> Secret Key is a **self-hosted** system — the security of your installation depends largely on your own server's configuration.

| | Practice |
|---|---|
| 📁 | Keep the `/private/` directory **outside** `public_html` |
| 🔒 | Use HTTPS (SSL/TLS) on the server |
| 🔄 | Regularly update PHP to the latest 8.x version |
| 🚫 | Never expose the `secret-key.php` file publicly |
| 📥 | Don't link directly to sensitive files in the public directory — serve them through `download.php` (requires a session, logs downloads) |
| 🔑 | Use strong, unique passwords for every account |
