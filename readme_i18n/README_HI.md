## विचार

हम में से हर कोई दर्जनों पासवर्ड रखता है — बैंकों, ईमेल, सोशल मीडिया, सब्सक्रिप्शन के लिए। **हमारी मृत्यु के बाद उनका क्या होता है?** परिवार खातों से पूरी तरह कट जाता है, सब्सक्रिप्शन रद्द नहीं कर पाता, खाते बंद नहीं कर पाता, पैसे वापस नहीं ले पाता।

Secret Key दो गारंटी के साथ एक सुरक्षित आपातकालीन योजना बनाकर इस समस्या को हल करता है:

| &nbsp; | समस्या | समाधान |
|---|---|---|
| 🔐 | मालिक के **जीवित रहते** अनधिकृत एक्सेस | हर एक्सेस प्रयास के लिए पासवर्ड + SMS कोड चाहिए |
| 💀 | **मृत्यु के बाद** खातों तक एक्सेस खोना | नामित लोग शमीर एल्गोरिथ्म से पासवर्ड को पुनर्निर्मित करते हैं |

यह सिस्टम **पूरी तरह से सेल्फ़-होस्टेड** है — डेटा कभी भी आपके सर्वर से बाहर नहीं जाता। कोई केंद्रीय डेटाबेस नहीं, कोई क्लाउड नहीं, SMS भेजने के अलावा कोई बाहरी निर्भरता नहीं।

<a name="stack"></a>

```
बैकएंड         PHP 8+, फ़्लैट फ़ाइलें (JSON + PHP कॉन्फ़िग), शून्य SQL
प्राधिकरण       bcrypt cost=10, SMSPlanet API के ज़रिए SMS 2FA
क्रिप्टोग्राफी   Shamir Secret Sharing (secrets.js)
फ्रंटएंड        सादा HTML + JS, शून्य बाहरी निर्भरताएँ (ऑफ़लाइन काम करता है)
```

## यह कैसे काम करता है

संकट की स्थिति में, नामित लोग चार चरण पूरे करते हैं:

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  01  इकट्ठा होना      5 में से कम से कम 3 नामित लोग                  │
│      ─────────       हर एक के पास कुंजी के टुकड़े वाला कार्ड है       │
│                                                                      │
│  02  लॉगिन           Secret Key कार्ड से लॉगिन जानकारी               │
│      ──────────      + असाइन किए गए फ़ोन नंबर पर SMS कोड             │
│                                                                      │
│  03  शेयर            हर व्यक्ति अपना शेयर डालता है या                │
│      ─────────       कार्ड का QR कोड स्कैन करता है                   │
│                                                                      │
│  04  एक्सेस           पासवर्ड ब्राउज़र में स्थानीय रूप से पुनर्निर्मित —│
│      ────────        जो कभी सर्वर तक नहीं पहुँचता                    │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

**खाते से जुड़े फ़ोन के बिना, लॉगिन करना असंभव है** — कार्ड की जानकारी जानते हुए भी।  
**शेयरों की आवश्यक संख्या के बिना, पासवर्ड को पुनर्निर्मित करना गणितीय रूप से असंभव है** — सर्वर तक एक्सेस होने पर भी।

## Secret Key कार्ड

हर नामित व्यक्ति को चार तत्वों वाला एक निजीकृत माध्यम मिलता है:

| तत्व | विवरण |
|---|---|
| 🔑 **लॉगिन और पासवर्ड** | अनूठी एक्सेस जानकारी — हर व्यक्ति का अपना खाता होता है जिसमें एक असाइन किया गया फ़ोन नंबर होता है |
| 🔢 **शमीर शेयर** | हेक्स फ़ॉर्मेट में एक कुंजी टुकड़ा — पाँच में से एक, बाकियों के बिना बेकार |
| ⊞ **QR कोड** | वही शेयर QR के रूप में एन्कोड किया गया — स्कैन करने से हाथ से लिखने की गलतियाँ खत्म हो जाती हैं |
| 🌐 **सिस्टम का पता** | आपके अपने Secret Key इंस्टेंस का URL — सीधे लॉगिन पैनल तक ले जाता है |

**माध्यम का फ़ॉर्मेट आपकी पसंद पर है** — प्रिंट किया हुआ पेज, PDF, प्लास्टिक कार्ड। महत्वपूर्ण यह है कि इसमें ऊपर बताए गए चार तत्व हों।

## शमीर एल्गोरिथ्म

Secret Key रहस्य को विभाजित और पुनर्निर्मित करने के लिए [`secrets.js`](https://github.com/amper5and/secrets.js) लाइब्रेरी का उपयोग करता है।

> [!NOTE]
> प्रयुक्त लाइब्रेरी [iancoleman.io/shamir](https://iancoleman.io/shamir/) द्वारा उपयोग की जाने वाली लाइब्रेरी के **समान** है — शेयर फ़ॉर्मेट पूरी तरह से संगत है, जो सिस्टम के बाहर स्वतंत्र सत्यापन की अनुमति देता है।

### रहस्य का विभाजन और पुनर्निर्माण

```
मास्टर पासवर्ड: "MyKeePassPassword2024!"
         │
         ▼  5 शेयरों में विभाजन (सीमा: 3)
         │
    ┌────┴──────────────────────────────────┐
    │                                       │
    │  S1: 801a3f9c2e4b7d1...  →  व्यक्ति A │  हर शेयर
    │  S2: 802c8f1a5e9b3d7...  →  व्यक्ति B │  बाकी की आवश्यक
    │  S3: 803e2a7f4c1b9d5...  →  व्यक्ति C │  संख्या के बिना
    │  S4: 804b6d3e8f2a1c9...  →  व्यक्ति D │  बेकार है
    │  S5: 805d9f7b2e4c3a1...  →  व्यक्ति E │
    │                                       │
    └────┬──────────────────────────────────┘
         │
         ▼  पुनर्निर्माण — 5 में से कोई भी 3 काफ़ी हैं
         │
    S1 + S2 + S3  →  "MyKeePassPassword2024!"  ✓
    S2 + S4 + S5  →  "MyKeePassPassword2024!"  ✓
    S1            →  रहस्य के बारे में कोई जानकारी नहीं  ✗
```

### क्रिप्टोग्राफ़िक गुण

रहस्य को क्षेत्र GF(2⁸) पर एक बहुपद के नियतांक पद के रूप में एन्कोड किया जाता है। हर शेयर उस बहुपद पर एक बिंदु है — आवश्यक संख्या में बिंदुओं को जानकर, लैग्रेंज इंटरपोलेशन के ज़रिए इसे विशिष्ट रूप से पुनर्निर्मित किया जा सकता है:

```
f(x) = a₀ + a₁x + a₂x² + ... + aₖ₋₁xᵏ⁻¹  (mod p)
```

> [!IMPORTANT]
> आवश्यक संख्या से **कम** शेयर रखने से रहस्य के बारे में **कोई भी** जानकारी नहीं मिलती (information-theoretic security)। अतिरिक्त 1024-बिट पैडिंग छोटे रहस्यों पर हमलों को रोकता है।

### इम्प्लीमेंटेशन पैरामीटर

| पैरामीटर | मान |
|---|---|
| लाइब्रेरी | secrets.js (amper5and) — iancoleman.io के साथ संगत |

| पुनर्निर्माण | ब्राउज़र साइड पर JavaScript — पासवर्ड कभी सर्वर तक नहीं पहुँचता |

## सिस्टम आर्किटेक्चर

सुरक्षित संसाधनों तक एक्सेस पाने से पहले उपयोगकर्ता क्रमिक रूप से कई सत्यापन स्तरों से गुज़रता है:

```
उपयोगकर्ता   →  लॉगिन + पासवर्ड दर्ज करता है
                         │
PHP सिस्टम   →  पासवर्ड सत्यापित करता है (bcrypt), रेट लिमिटिंग और CSRF जाँचता है
                         │
SMS / 2FA    →  असाइन किए गए नंबर पर एक बार का कोड भेजता है
                         │
उपयोगकर्ता   →  SMS कोड दर्ज करता है
                         │
PHP सिस्टम   →  कोड सत्यापित करता है, सेशन बनाता है, वैकल्पिक रूप से डिवाइस याद रखता है
                         │
ब्राउज़र      →  शमीर शेयर प्राप्त करता है, JS में स्थानीय रूप से रहस्य पुनर्निर्मित करता है
```

### सिस्टम की परतें

**प्राधिकरण परत** (`/app/`)
- `login.php` — लॉगिन फ़ॉर्म
- `auth.php` — सेशन लॉजिक, bcrypt, 2FA, ब्रूट-फ़ोर्स सुरक्षा, CSRF, साथ ही सहायक फ़ंक्शन `t()` (UI टेक्स्ट), `md_lite()` (मार्कडाउन-लाइट), `empty_state_box()`
- `verify.php` — SMS कोड सत्यापन
- `resend.php` — SMS पुनः भेजना
- `logout.php` — लॉगआउट

**एक्सेस परत** (`/decrypt/`)
- `index.php` — JS में शमीर पुनर्निर्माण के साथ डिक्रिप्शन पैनल
- `download.php` — नियंत्रित फ़ाइल डाउनलोड (सेशन आवश्यक, कॉन्फ़िगरेशन से बनी व्हाइटलिस्ट, सर्वर-साइड लॉगिंग)
- `log.php` — इवेंट लॉगिंग
- `devtools-log.php` — DevTools जाँच के प्रयासों की लॉगिंग (प्रति-IP रेट लिमिटिंग के साथ)

**डेटा परत** (`/private/` — `public_html` के बाहर)
- `secret-key.php` — एक ही कॉन्फ़िगरेशन फ़ाइल: लोग (`$people`), डाउनलोड योग्य फ़ाइलें (`$downloads`), निर्देश (`$instructions`), ईमेल सूचना (`$email_notify`), SMS डोमेन
- `lang.php` — इंटरफ़ेस टेक्स्ट (केवल एक भाषा, कोई स्विचर नहीं — देखें [इंस्टॉलेशन](#इंस्टॉलेशन))
- `rate-limit.php` — स्थायी रेट लिमिटिंग (सेशन से स्वतंत्र काउंटर)
- `rate_limits.json` — IP/खाते के अनुसार लॉगिन प्रयास काउंटर *(स्वचालित रूप से बनता है)*
- `trusted_devices.json` — विश्वसनीय डिवाइस टोकन *(स्वचालित रूप से बनता है)*
- `secret-key.log` — इवेंट लॉग
- `moja-baza-hasel.kdbx` *(और अन्य डाउनलोड योग्य फ़ाइलें)* — केवल `download.php` के ज़रिए उपलब्ध, कभी सीधे HTTP से नहीं

> [!WARNING]
> सभी संवेदनशील कॉन्फ़िगरेशन फ़ाइलें सर्वर के **पब्लिक डायरेक्टरी के बाहर** संग्रहीत हैं — वेब सर्वर की ग़लत कॉन्फ़िगरेशन से उन्हें उजागर होने का जोखिम नहीं है।

## सुरक्षा

यह सिस्टम **आठ स्वतंत्र सुरक्षा परतों** को जोड़ता है — एक परत को भेदने से सिस्टम तक एक्सेस नहीं मिलता।

| परत | तंत्र | विवरण |
|---|---|---|
| 🔒 **पासवर्ड** | bcrypt | cost=10, `$2y$` फ़ॉर्मेट, टाइमिंग-अटैक-प्रतिरोधी सत्यापन |
| 🛡️ **CSRF** | 64-हेक्स टोकन | क्रिप्टोग्राफ़िक रूप से जनरेट, हर स्टेट बदलने वाले एंडपॉइंट पर सत्यापित (लॉगिन, 2FA सत्यापन, SMS पुनः भेजना, इवेंट लॉग) |
| 🚫 **ब्रूट-फ़ोर्स** | रेट लिमिटिंग | 15 मिनट की विंडो में प्रति-IP 3 प्रयास + प्रति-खाता 3 प्रयास; प्रति घंटा 3 ग़लत SMS कोड। सर्वर-साइड स्थायी काउंटर (एक फ़ाइल, क्लाइंट के सेशन/कुकीज़ से स्वतंत्र) |
| 📱 **SMS 2FA** | 6-अंकीय कोड | क्रिप्टोग्राफ़िक रूप से जनरेट, 10 मिनट के लिए वैध, भेजने के बीच 60 सेकंड की कूलडाउन |
| 💻 **विश्वसनीय डिवाइस** | SHA-256, HttpOnly | Secure + SameSite=Strict, `public_html` के बाहर फ़ाइल, 7-दिन TTL |
| ⏱️ **सेशन** | ऑटो-लॉगआउट | स्पष्ट HttpOnly + Secure + SameSite=Strict फ़्लैग वाला सेशन कुकी; 30-मिनट टाइमआउट, हर सत्यापन के बाद सेशन ID पुनः जनरेट |
| 🖥️ **इंटरफ़ेस सुरक्षा** | DevTools पहचान | डेवलपर टूल्स को पहचानता है, DOM को शारीरिक रूप से हटाता है, IP, REF# और अवधि के साथ घटना लॉग करता है |
| 📥 **नियंत्रित डाउनलोड** | `download.php` + व्हाइटलिस्ट | डाउनलोड योग्य फ़ाइलें `public_html` के बाहर हैं; एक्टिव सेशन आवश्यक, कोई डायरेक्ट URL नहीं, हमेशा सर्वर साइड पर लॉग किया जाता है |

### चरण 1 — कॉन्फ़िगरेशन (ऑफ़लाइन)

अपने ब्राउज़र में स्थानीय रूप से `dashboard.html` खोलें। इसमें दो टैब हैं:

**कॉन्फ़िगरेशन** — `secret-key.php` फ़ाइल जनरेट करता है:
1. SMSPlanet API टोकन, SMS भेजने वाले का नाम, और कोड ऑटो-फ़िल के लिए डोमेन (Android/iOS) — केवल डोमेन, `@` और `https://` के बिना
2. हर नामित व्यक्ति के लिए: लॉगिन, पासवर्ड, पहला नाम, अंतिम नाम, फ़ोन नंबर, और क्या वे पैनल में धारक सूची में दिखें
3. डाउनलोड योग्य फ़ाइलें (पासवर्ड डेटाबेस, 2FA डेटाबेस, प्रोग्राम इंस्टॉलर) — कुंजी, बटन लेबल, फ़ाइल नाम
4. पैनल के लिए निर्देश चरण (फ़ॉर्मेटिंग: `**बोल्ड**` / `*इटैलिक*`)
5. वैकल्पिक: हर लॉगिन पर ईमेल सूचना (प्राप्तकर्ता का पता, भेजने वाला, पैनल लिंक)
6. "कॉन्फ़िगरेशन जनरेट करें" पर क्लिक करें और जनरेट की गई `secret-key.php` फ़ाइल डाउनलोड करें

**एन्क्रिप्शन** — मास्टर पासवर्ड को शमीर शेयरों में विभाजित करता है:
1. पासवर्ड डेटाबेस का मास्टर पासवर्ड दर्ज करें
2. शेयरों की कुल संख्या और आवश्यक न्यूनतम सेट करें
3. "शेयर जनरेट करें" पर क्लिक करें
4. `secret-key-shares.txt` फ़ाइल डाउनलोड करें

> [!TIP]
> दोनों टूल **पूरी तरह से ऑफ़लाइन** काम करते हैं — कोई भी डेटा ब्राउज़र से बाहर नहीं जाता। फ़ॉर्म हर बार चलाने पर `secret-key.php` को शुरू से जनरेट करता है — यह किसी मौजूदा फ़ाइल को लोड या एडिट नहीं करता।

### चरण 2 — सर्वर पर अपलोड करना

```bash
/home/user/
├── public_html/
│   ├── app/           ← /app/ फ़ोल्डर की सामग्री
│   └── decrypt/       ← /decrypt/ फ़ोल्डर की सामग्री
└── private/           ← public_html के बाहर
    ├── secret-key.php  ← जनरेट की गई कॉन्फ़िगरेशन फ़ाइल
    ├── lang.php        ← इंटरफ़ेस टेक्स्ट (एक भाषा, चरण 1 देखें)
    ├── rate-limit.php  ← रिपॉज़िटरी से एक सिस्टम फ़ाइल (रेट लिमिटिंग)
    └── moja-baza-hasel.kdbx  ← आपकी फ़ाइलें (download.php के ज़रिए उपलब्ध)
```

> [!WARNING]
> `lang.php` को `secret-key.php` के **साथ ही** सर्वर पर अपलोड किया जाना चाहिए। `auth.php` इसे `require_once` के ज़रिए लोड करता है — फ़ाइल के गायब होने से पूरा सिस्टम क्रैश हो जाता है (हर पेज पर एक फ़ेटल एरर), न कि केवल अनुवाद।

### चरण 4 — SMS सामग्री में डोमेन (WebOTP)

भेजे गए SMS कोड की सामग्री `@डोमेन #कोड` वाली लाइन पर समाप्त होती है — यह [WebOTP API](https://developer.mozilla.org/en-US/docs/Web/API/WebOTP_API) द्वारा आवश्यक फ़ॉर्मेट है, जिसकी मदद से फ़ोन का ब्राउज़र SMS से हाथ से टाइप किए बिना कोड फ़ील्ड को स्वयं भर देता है।

आप डोमेन को **चरण 1** में, डैशबोर्ड फ़ॉर्म में ("SMS ऑटोफ़िल डोमेन" फ़ील्ड) सेट करते हैं — आप केवल डोमेन दर्ज करते हैं, `@` और `https://` के बिना (डैशबोर्ड स्वचालित रूप से `@` जोड़ता है)। यह कॉन्फ़िगरेशन में इस तरह जाता है:

```php
define('SMS_AUTOFILL_DOMAIN', '@your-domain.com');
```

> [!WARNING]
> डोमेन का उस डोमेन से **पूरी तरह** मेल खाना चाहिए जिसके अंतर्गत आप सिस्टम को होस्ट करते हैं — अन्यथा WebOTP SMS को अनदेखा कर देगा और ऑटोफ़िल काम नहीं करेगा। कोड फिर भी पहुँचेगा और हाथ से दर्ज करने पर काम करेगा, केवल इस सुविधा के बिना।

### चरण 5 — कार्डों का वितरण

हर नामित व्यक्ति के लिए, इनके साथ एक माध्यम तैयार करें:
- लॉगिन और पासवर्ड (कॉन्फ़िगरेशन टैब से)
- एक शमीर शेयर (`secret-key-shares.txt` फ़ाइल से)
- वैकल्पिक रूप से: वही शेयर वाला QR कोड
- आपके सिस्टम इंस्टेंस का पता

## अक्सर पूछे जाने वाले सवाल

<details>
<summary><strong>अगर मैं अपना Secret Key कार्ड खो दूँ तो क्या होगा?</strong></summary>

कार्ड अकेला उस खाते से जुड़े फ़ोन तक एक्सेस के बिना बेकार है — लॉगिन के लिए SMS सत्यापन चाहिए। जोखिम सीमित है, फिर भी मालिक को सूचित किया जाना चाहिए और शेयरों के नए सेट के साथ नई कॉन्फ़िगरेशन जनरेट करने पर विचार करना चाहिए।

</details>

<details>
<summary><strong>क्या मैं सिर्फ़ एक कार्ड से अकेले पासवर्ड पढ़ सकता हूँ?</strong></summary>

नहीं। यह गणितीय रूप से असंभव है। एक ही शेयर रहस्य के बारे में कोई जानकारी प्रकट नहीं करता — यह एल्गोरिथ्म का एक गुण है जिसे information-theoretic security कहा जाता है। मास्टर पासवर्ड को पुनर्निर्मित करने के लिए केवल आवश्यक संख्या में शेयर इकट्ठा करना ही काफ़ी है।

</details>

<details>
<summary><strong>अगर नामित लोगों में से कोई मर जाए या अनुपलब्ध हो जाए तो क्या होगा?</strong></summary>

यह सिस्टम अतिरेक (redundancy) के साथ डिज़ाइन किया गया है — शेयरों की न्यूनतम आवश्यक संख्या इकट्ठा करना काफ़ी है (जैसे 5 में से 3)। एक या दो लोगों की अनुपलब्धता आपातकालीन प्रक्रिया को नहीं रोकती, जब तक बाकी लोग इकट्ठा हो सकें।

</details>

<details>
<summary><strong>डिक्रिप्शन के दौरान क्या पासवर्ड सर्वर तक पहुँचता है?</strong></summary>

नहीं। शमीर शेयरों से पासवर्ड का पुनर्निर्माण **पूरी तरह से ब्राउज़र साइड** (JavaScript) पर होता है। सर्वर का उपयोग केवल उपयोगकर्ता को प्रमाणित करने के लिए किया जाता है — रहस्य स्वयं कभी उसे नहीं छोड़ता।

</details>

<details>
<summary><strong>क्या मैं KeePassXC के अलावा किसी अन्य पासवर्ड मैनेजर के साथ इस सिस्टम का उपयोग कर सकता हूँ?</strong></summary>

हाँ। Secret Key **किसी भी मास्टर पासवर्ड** को संग्रहीत और पुनर्निर्मित करता है — उपयोग किए गए मैनेजर पर निर्भर नहीं करता। मास्टर पासवर्ड को सपोर्ट करने वाले किसी भी प्रोग्राम के साथ संगत: KeePassXC, Bitwarden, 1Password और अन्य।

</details>

<details>
<summary><strong>सीमा कैसे चुनें — कितने शेयरों की ज़रूरत है?</strong></summary>

सीमा जितनी अधिक होगी, सुरक्षा उतनी अधिक होगी — लेकिन संकट की स्थिति में सभी को इकट्ठा करना भी उतना ही कठिन होगा। स्टैंडर्ड उपयोग के लिए अनुशंसित समझौता है **5 में से 3** — यह अच्छे स्तर की सुरक्षा बनाए रखते हुए दो लोगों की अनुपलब्धता को सहन करता है।

</details>

<details>
<summary><strong>कार्ड की लॉगिन जानकारी कितने समय तक वैध रहती है?</strong></summary>

अनिश्चित काल तक — जब तक मालिक नई कॉन्फ़िगरेशन जनरेट नहीं करता और सर्वर पर `secret-key.php` फ़ाइल को बदल नहीं देता। इस कार्रवाई के बाद, पुराने कार्ड काम करना बंद कर देते हैं और सभी नामित लोगों को नए कार्ड वितरित करने होते हैं।

</details>
